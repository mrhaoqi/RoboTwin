# 面向新型机械臂本体的 RoboTwin 平台适配与模仿学习实验

## —— 从单臂兼容、本体接入到侧装构型的数据采集与策略训练

**实验周期**：2025-09 ~ 2026-08
**平台**：RoboTwin（SAPIEN 仿真）+ curobo 运动规划
**硬件**：NVIDIA RTX 4090 Laptop（16 GB）
**状态**：已完成本体接入、位姿标定、数据采集与两轮训练评估；
第 9 节定位并修复了一处平台级缺陷；300 条数据的验证性重训进行中（第 10 节）

---

## 摘要

本工作以 RoboTwin 双臂机器人仿真平台为基础，完成了将第三方六自由度单臂机械臂
RM65-B 接入平台并用于模仿学习的完整链路，涵盖平台架构适配、本体建模、
安装位姿标定、数据采集、策略训练与评估五个环节。

主要工作与发现：

1. **单臂本体在双臂平台上的兼容方案**。RoboTwin 的任务逻辑与数据格式均围绕双臂设计，
   本工作利用平台的"同一本体兼任左右臂"机制，使单臂机械臂无需修改任务代码即可
   执行全部单臂任务，并保持数据格式与双臂本体一致。

2. **提出一个反直觉的安装位姿标定结论**。实验表明，机械臂安装位姿不能仅按运动学
   可达距离选取：可达裕度最大的候选位置反而采集效率最差（规划失败 0 次却需 58 次
   尝试才采满 2 条轨迹）。真正的瓶颈在于**末端接近目标时的姿态可行性**而非能否触及。
   据此改用实测扫描法定位，最终位姿相比按距离模型选出的位姿，采集效率提升 **3 倍以上**。

3. **完成侧装构型 4 项任务共 200 条专家轨迹的采集**，并与既有桌面装构型数据合并，
   训练 4 个 ACT 策略模型（22 小时 15 分）与 1 个 TinyVLA 模型（5 小时 03 分）。

4. **提出跨安装构型的数据混合训练方案**，使单一策略同时学习两种安装姿态，
   为实机部署时的构型变化提供泛化基础。两种架构的训练过程均表明，
   引入第二种安装构型未增加收敛难度（TinyVLA 混合模型在同等 epoch 下的
   末段 loss 与纯单构型基线相当）。

5. **评估阶段得到一个负面结果，但其解读经历了一次重要修正**（第 10 节）。
   所有模型的成功率均接近 0，据此曾推断模型存在严重缺陷，并展开多轮修复。
   直至让**专家策略**（拥有完美物体位姿与运动规划器）在同一批评估场景上运行，
   才发现其成功率也仅 **15.3 %** —— 评估脚本按 seed 顺序取样、不筛选场景可行性，
   模型成功率的**理论上限本就约为 1/3 而非 100 %**。
   由此可知："0/15" 的真实对照是专家的 "5/15"，此前的解读系统性高估了问题的严重程度；
   且样本量 15、可成功位仅 5 的设置下，统计分辨率不足以体现各轮修复的改善。
   修正方法是**仅在专家验证过可完成的场景上评估**，使上限回到 100 %，
   将"任务难度"与"模型能力"解耦。
   **推广的教训：报告任何成功率之前，应先测量该指标的可达上限。**

6. **定位到一处平台级缺陷：单臂本体的夹爪指令相互覆盖**（第 9 节）。
   RoboTwin 允许单臂机械臂"兼任左右臂"以复用双臂任务代码，但仿真执行时
   会对左右两侧分别下发夹爪指令，而二者指向同一物理关节，后者覆盖前者，
   导致夹爪逐帧震荡、无法夹持物体。诊断显示模型的夹爪预测其实完全正确
   （被选中侧从 0.908 降至 0，另一侧稳定在 0.98），是执行环节破坏了它。
   该缺陷影响任何单臂本体的抓取类任务，修复仅需 22 行且不触及双臂路径。

7. **两套策略框架的部署链路共发现 7 处"训练—部署不一致"缺陷**
   （ACT 2 处、TinyVLA 5 处），其中 TinyVLA 的评估路径此前从未被完整跑通。
   这类缺陷分两种形态：一种令程序直接崩溃，易于发现；
   另一种令程序照常运行却产出无效结果（如加载末轮权重、相机顺序颠倒、
   视觉 token 数相差 12 倍），危险得多。
   由此提炼出的做法是：**在采信任何评估数字之前，先用开环回放验证执行链路、
   用观测比对验证输入分布** —— 这两项检查成本很低，却能区分
   "模型不行"与"链路有问题"这两种截然不同的结论。

8. 记录了一类**隐蔽的环境故障模式**：Python 包 ABI 不匹配在深层调用栈中表现为
   完全无关的属性缺失异常，极易误判为业务逻辑缺陷。

## 1. RoboTwin 平台概述

### 1.1 平台定位

RoboTwin 是面向双臂机器人操作任务的仿真数据生成与策略评测平台，
基于 SAPIEN 物理引擎构建。其核心价值在于以专家轨迹的自动化生成替代人工遥操作采集，
从而低成本地产出大规模模仿学习训练数据。

平台当前包含 **50 项操作任务**，支持 **7 种机器人本体**，
并集成了 ACT、DP、DP3、RDT、pi0、TinyVLA、DexVLA、openvla-oft 等
**9 类策略基线**的训练与评测流程。

### 1.2 核心架构

平台采用分层设计，各层职责如下：

| 层次 | 组件 | 职责 |
|---|---|---|
| 任务层 | `envs/<task>.py` | 定义物体生成、动作序列、成功判据 |
| 基类层 | `envs/_base_task.py` | 场景构建、本体加载、相机、观测、动作执行 |
| 本体层 | `envs/robot/robot.py` + `assets/embodiments/` | 本体加载、运动规划接口 |
| 规划层 | curobo / mplib | 逆运动学与轨迹规划 |
| 策略层 | `policy/<name>/` | 数据预处理、训练、部署 |

**任务与本体解耦**是平台的关键设计。任务代码只描述"做什么"
（抓取某物体、移动到某位姿），不涉及具体本体的运动学参数；
本体的全部差异集中于 `assets/embodiments/<name>/config.yml`。
这一解耦使得新增本体在理想情况下无需改动任何任务代码。

### 1.3 数据生成流程

```
seed 搜索阶段：随机场景 → 规划求解 → 执行 → 成功判据
                    ↓ 失败则换 seed 重试
              记录可行 seed
                    ↓
回放采集阶段：按 seed 复现场景 → 执行 → 录制观测与动作 → 存 HDF5
```

两阶段设计的意义在于：seed 搜索阶段不录制数据，因而可以高频重试；
只有确认可完成的场景才进入采集阶段。这也意味着**采集效率的瓶颈在于 seed 成功率**，
该指标同时受任务难度、域随机化强度和本体运动学能力三方面影响 ——
这一点在第 4 节的位姿标定中被用作核心评价指标。

## 2. 单臂本体的兼容适配

### 2.1 问题

RoboTwin 面向双臂机器人设计，其数据结构与任务逻辑存在如下双臂假设：

- 观测与动作均分为 `left_arm` / `right_arm` 两组，状态维度固定为 14；
- 任务代码通过 `arm_tag` 选择使用哪条臂，例如 `place_object_stand` 依据物体的
  x 坐标决定用左臂还是右臂：
  ```python
  arm_tag = ArmTag("right" if self.object.get_pose().p[0] > 0 else "left")
  ```
- 基类在初始化与执行阶段均会访问 `left_entity` / `right_entity`、
  `left_planner` / `right_planner` 等成对属性。

而 RM65-B 是单臂机械臂。若为其单独编写任务逻辑，则平台已有的 50 项任务无法复用，
且产出的数据格式与双臂本体不一致，无法共用策略训练代码。

### 2.2 兼容机制

平台通过 `task_config` 中 `embodiment` 字段的**长度**区分两种模式
（`script/collect_data.py`）：

```python
if len(embodiment_type) == 1:
    # 单一本体同时充当左右臂
    args["left_robot_file"]  = get_embodiment_file(embodiment_type[0])
    args["right_robot_file"] = get_embodiment_file(embodiment_type[0])
    args["dual_arm_embodied"] = True
elif len(embodiment_type) == 3:
    # 两个独立本体 + 间距
    args["left_robot_file"]  = get_embodiment_file(embodiment_type[0])
    args["right_robot_file"] = get_embodiment_file(embodiment_type[1])
    args["embodiment_dis"]   = embodiment_type[2]
    args["dual_arm_embodied"] = False
```

对应地，`Robot` 类在加载实体时有两条路径（`envs/robot/robot.py`）：

```python
if self.is_dual_arm:
    # 加载一次 URDF，左右臂指向同一实体
    self._entity = loader.load(self.left_urdf_path)
    self.left_entity  = self._entity
    self.right_entity = self._entity
else:
    # 加载两个独立实体，沿 x 轴左右分开 embodiment_dis
    self.left_entity_origion_pose.p  += [-arms_dis / 2, 0, 0]
    self.right_entity_origion_pose.p += [ arms_dis / 2, 0, 0]
    self.left_entity  = left_loader.load(self.left_urdf_path)
    self.right_entity = right_loader.load(self.right_urdf_path)
```

此处存在一处易混淆的命名：单臂本体应配置为 **`embodiment: [rm65b]`（长度 1）**，
此时 `dual_arm_embodied = True` —— 该标志的语义是"左右臂由同一实体承担"，
而非"这是一台双臂机器人"。本体配置文件中另有 `dual_arm: False` 字段，
描述的才是机械臂本身的物理形态。二者含义不同，不可混淆。

### 2.3 适配要点

在此机制下接入单臂本体，需满足以下条件：

1. **`config.yml` 中左右臂参数成对声明**。`move_group`、`ee_joints`、
   `arm_joints_name`、`gripper_name` 等字段均为长度 2 的列表，
   单臂本体将两项填为相同值：
   ```yaml
   move_group: ["r_link6", "r_link6"]
   arm_joints_name: [["joint1", ..., "joint6"],
                     ["joint1", ..., "joint6"]]
   ```

2. **curobo 规划配置需区分左右**。当左右臂使用同一 URDF 时，
   平台会将 `curobo.yml` 替换为 `curobo_left.yml` / `curobo_right.yml`；
   若左右配置路径相同，则在同一进程内构造两个规划器，否则启用多进程通信模式
   （`communication_flag`）。因此新增本体必须准备完整的 curobo 模板文件，
   并通过 `script/update_embodiment_config_path.py` 将其中的 `${ASSETS_PATH}`
   占位符替换为绝对路径。

3. **任务的选臂逻辑自动生效**。由于左右臂指向同一实体，
   任务中依据物体位置选择 `arm_tag` 的逻辑无需改动即可运行 ——
   无论选中哪条"臂"，实际执行的都是同一台机械臂。

4. **数据格式保持一致**。观测与动作仍按 14 维双臂格式存储，
   左右两组数据相同。这使得单臂数据可直接复用平台的全部策略训练代码。

### 2.4 适配范围的限制

该机制仅适用于**单臂即可完成的任务**。平台中涉及双臂协同的任务
（如 `handover_block` 物体交接、`pick_dual_bottles` 双瓶同抓）
在单臂本体下不可行，因为它们要求两条臂同时处于不同位姿。

本工作使用的 4 项任务均为单臂任务。

## 3. RM65-B 本体接入

### 3.1 接入内容

将新本体接入平台需完成以下工作：

| 项目 | 位置 | 说明 |
|---|---|---|
| URDF / SRDF | `assets/embodiments/rm65b/` | 连杆、关节、碰撞体定义 |
| 本体配置 | `.../config.yml` | 关节名、夹爪、安装位姿、相机 |
| curobo 模板 | `.../curobo{,_left,_right}_tmp.yml` | 规划器的运动学与碰撞配置 |
| 本体注册 | `task_config/_embodiment_config.yml` | 名称到路径的映射 |
| 路径展开 | `script/update_embodiment_config_path.py` | 将模板中的占位符替换为绝对路径 |

注册项形如：

```yaml
rm65b:
  file_path: "./assets/embodiments/rm65b"
```

### 3.2 夹爪配置

RM65-B 配用的四连杆平行夹爪包含多个从动关节，通过 `mimic` 机制描述联动关系：

```yaml
gripper_name:
  - base: "4C2_Joint1"
    mimic: [["4C2_Joint4", -1., 0.], ["4C2_Joint5", 1., 0.], ["4C2_Joint6", 1., 0.]]
gripper_bias: 0.145      # 夹爪尖相对法兰的偏移，参与末端位姿计算
gripper_scale: [0, 0.82] # 开合行程
```

`gripper_bias` 需与实际几何一致，否则抓取位姿会系统性偏移。

### 3.3 腕部相机标定

接入过程中发现，腕部相机的初始朝向存在偏差，导致部分任务的腕部视角完全无效
（`place_object_stand` 任务腕部相机有效率为 0，`turn_switch` 为 58 %）。
经排查为 URDF 中相机关节的姿态设置问题，将 rpy 由 `[-0.33, -1.57, 0]`
修正为 `[0.027, 0.814, 0.005]` 后解决。

此问题的隐蔽之处在于：腕部视角无效不会导致任何报错，仅表现为策略性能不佳，
若不逐帧检视采集到的图像很难发现。

### 3.4 版本管理的注意事项

`assets/embodiments/` 目录被 `.gitignore` 排除，因此本体的 URDF、config.yml
及 curobo 配置均不受版本管理。上述相机修正、位姿参数等关键改动仅存在于本地文件，
需另行备份。

## 4. 侧装构型的建模与位姿标定

### 4.1 动机

平台内既有本体均采用**桌面装**构型：基座固定于桌面外侧，臂体自下向上朝台面伸展。
而实际部署中，机械臂常安装于**升降柱侧面**，基座截面朝向侧方，
臂体的展开方向与桌面装存在本质差异。

两种构型下，同一任务的关节轨迹分布、末端接近角度与相机视角均不相同。
若策略仅在单一构型数据上训练，迁移至另一构型时性能将显著退化。
为此建立侧装构型本体 `rm65b_lateral`。

### 4.2 本体定义

侧装构型与桌面装构型**共用同一 URDF 与 SRDF**，仅安装位姿与相机外参不同：

```yaml
urdf_path: "../rm65b/urdf/rm65b.urdf"
srdf_path: "../rm65b/rm65b.srdf"
```

这一设计保证两种构型的运动学参数完全一致，使后续的数据混合具备物理合理性 ——
两批数据的差异纯粹来自安装姿态，而非机械结构。

**姿态四元数**：`[0.5, -0.5, 0.5, 0.5]`

需注意，平台通过 `sapien.Pose(p, q)` 解析该字段，其四元数顺序为 **`[w, x, y, z]`**，
而非配置文件原注释所述的 `[qx, qy, qz, qw]`。此姿态下基座局部 +Z 轴
（臂体伸出方向）指向世界坐标系 +Y 方向，因此基座必须置于工作台的 -Y 侧，
臂体方可朝向台面展开。初始配置 `[0, 0, 1.0]` 将基座置于台面正上方，
臂体自桌面上方伸向桌外，方向完全相反。

### 4.3 臂展模型

由 URDF 连杆参数可得：

| 分段 | 长度 (m) | 说明 |
|---|---|---|
| base_link → joint1 | 0.2405 | 立柱段，沿 +Z 推出肩部，**不参与摆动** |
| joint2 → joint3 | 0.2560 | 大臂 |
| joint3 → joint4 | 0.2100 | 小臂 |
| joint5 → joint6 | 0.1120 | 腕部 |
| 法兰 + 夹爪 | 0.1750 | 含 `gripper_bias` 0.145 |

**肩部工作半径 = 0.753 m**（joint2 至夹爪尖），这才是可达性的真实约束；
立柱段仅将肩部平移，不扩大工作球半径。该值与 RM65-B 实机标称
（至法兰 610 mm + 夹爪约 175 mm ≈ 785 mm）吻合。

一个易犯的错误是将立柱段计入臂展，得到 0.9935 m 的"理论最远距离"，
并据此认为基座可后移更远。本实验初期正是因此而选择了错误的位姿。

### 4.4 工作台与任务空间

工作台由 `envs/_base_task.py` 构建：长 1.2 m、宽 0.7 m、台面高 0.74 m，
即 x ∈ [-0.6, 0.6]，y ∈ [-0.35, 0.35]。各任务的物体生成区域远小于整个台面：

| 任务 | x 范围 | y 范围 | 特点 |
|---|---|---|---|
| adjust_bottle | [-0.12, 0.12] | [-0.13, -0.08] | 近端，区域最小 |
| shake_bottle | [-0.15, 0.15] | [-0.15, -0.05] | 近端 |
| place_object_stand | [-0.28, 0.28] | [-0.05, 0.05] | 中部 |
| turn_switch | [-0.25, 0.25] | [0.0, 0.1] | 远端，开关随机朝向 |

注意平台中另有部分任务（如 `pick_diverse_bottles`、`put_bottles_dustbin`）
的物体生成区域延伸至 y = 0.23，超出侧装构型在任何合理安装位置下的可达范围，
故未纳入本实验。

### 4.5 位姿标定方法的演进

**阶段一：几何推算**。按"基座 +Z 指向 +Y、须置于 -Y 侧"的约束，
参照桌面装构型的 y = -0.45，将基座设于 y = -0.45、z = 1.0。

**阶段二：距离模型优化**。考虑到 RM65-B 相对本任务尺度偏长，
装得过近过矮会在运动过程中扫到台面物品，遂尝试后移抬高。
以（错误的）0.9935 m 臂展模型计算，得出 y = -0.70、z = 1.20 仍有约 4 cm 裕度，遂采用之。

**阶段三：实测扫描**。阶段二的位姿在冒烟测试中暴露严重问题 ——
`turn_switch` 失败 36/38 次。遂设计位姿扫描实验，以**采满固定条数数据所需的
seed 尝试次数**作为效率指标，对候选位姿逐一实测。

### 4.6 扫描实验结果

评测任务：`turn_switch`（该任务对末端姿态最敏感，开关随机朝向且须从正面拨动）。

| 基座 (y, z) | 高于台面 | 尝试次数 | 其中规划失败 | 按距离模型的裕度 |
|---|---|---|---|---|
| (-0.70, 1.20) | 46 cm | 38 / 2 条 | 3 | 4.2 cm |
| (-0.60, 1.15) | 41 cm | **58 / 2 条** | **0** | 14.5 cm |
| (-0.50, 1.10) | 36 cm | 17 / 3 条 | 0 | 24.4 cm |
| **(-0.70, 1.05)** | **31 cm** | **12 / 3 条** | **0** | 10.5 cm |
| (-0.70, 0.95) | 21 cm | 10 / 3 条 | 0 | 13.0 cm |

### 4.7 核心发现

**发现一：可达裕度与采集效率不成正比。**

(-0.60, 1.15) 一组的**运动规划失败次数为 0**，说明目标位姿在运动学上完全可达；
但它却是所有候选中效率最差的一组，比裕度更小的 (-0.70, 1.20) 还差 50 %。
这说明失败并非发生在"能否到达目标点"，而在于**到达之后能否以任务所需的姿态完成操作**。

`turn_switch` 要求末端从开关正面接近并拨动。基座装得过高时，
腕部被迫以别扭的角度向下探，虽然位置可达，但夹爪朝向无法满足拨动条件。
**纯位置的距离模型对这一约束完全不敏感。**

**发现二：降低安装高度可同时优化两个相互冲突的目标。**

实验初期认为"基座远离桌面"与"采集效率"存在权衡：后移可减少碰撞风险，但会牺牲可达性。
扫描结果推翻了这一判断 —— 在保持基座位于最远处（y = -0.70）的前提下，
仅将高度由 1.20 m 降至 1.05 m，效率即提升 3 倍以上。降低高度改善了末端接近姿态，
而基座的水平距离得以保留。

**发现三：极端值不必取。**

(-0.70, 0.95) 虽略优于 (-0.70, 1.05)，但其高出台面仅 21 cm，
运动过程中的避让空间明显收窄。考虑到边际收益甚微而碰撞风险上升，最终未予采用。

### 4.8 定案与方法论建议

```yaml
robot_pose: [[0, -0.70, 1.05, 0.5, -0.5, 0.5, 0.5]]
```

基座位于桌沿外 35 cm、高出台面 31 cm。

由此提炼出的位姿标定流程为**"距离模型缩小范围 + 实测扫描定案"**：

1. 用运动学可达模型排除明显不可行的候选（如本实验中 y ≤ -0.75 必然超出工作半径）；
2. 在剩余候选中，以实际任务的采集效率为指标进行小规模实测
   （每组 2–3 条数据即可显现差异）；
3. **不得直接采用距离模型的最优解。**

此外，修改本体位姿后原有 seed 文件立即失效，必须更换 task_config 名称重新搜索，
否则旧 seed 在新构型下回放将在采集阶段触发 `Collect Error`。

### 4.9 相机配置

头部相机位姿随基座调整，但保持与桌面装构型相同的**后上方俯视朝向**
（`forward = [0, 0.6, -0.8]`）。这一点对后续数据混合至关重要：
若两种构型的相机视角差异过大，视觉特征分布的偏移将掩盖构型本身的差异，
使混合训练难以收敛。

| 相机 | 型号 | 分辨率 | FOV |
|---|---|---|---|
| head_camera | L515 | 320×180 | 45° |
| wrist_camera (×2) | D435 | 320×240 | 37° |

## 6. 模仿学习训练

### 6.1 数据组织

既有的桌面装构型数据覆盖 4 项任务（各 50 条），其中 `place_object_stand` 与
`turn_switch` 与本次采集的任务重合，因而可构成混合数据集：

（TinyVLA 的 `dataset_dir` 字段原生支持目录列表与 `sample_weights`，

### 6.3 训练结果

| 任务 | 训练集 | 最优 val loss | 最优 epoch | 耗时 |
|---|---|---|---|---|

| turn_switch | 混合 100 | 0.2046 | 5581 | 7 h 10 m |

### 6.4 训练过程分析

**总损失曲线健康。** 训练损失与验证损失同步下降、无背离，
约 1000 epoch 后收敛并保持平稳。混合数据（两种安装姿态）的引入未造成训练不稳定。

**L1 指标显示过拟合。** 以 `place_object_stand` 为例，训练集 L1 降至约 0.03，
验证集 L1 稳定在约 0.30，二者相差约一个数量级，且自 1000 epoch 起差距不再收窄。
100 条轨迹训练 6000 epoch 确实偏多。此外验证集 L1 波动范围较大（0.15–0.55），
提示不同样本的难度差异显著，可能与混合数据中两种构型的分布差异有关。

**不同训练集的 loss 不可直接横向比较。** 混合数据集的 loss 高于纯侧装数据集，
但这既反映了"模型需同时拟合两种构型"的难度，也反映了任务本身的复杂度差异
（`adjust_bottle` 仅调整物体姿态，不涉及抓取与搬运）。因此 0.0381 与 0.1343 之间
不构成优劣关系。

**turn_switch 未充分收敛。** 其最优 epoch 为 5581（总数 6000），接近训练末端，
提示继续增加 epoch 仍可能有收益。该任务在桌面装构型下的历史成功率亦仅约 58 %，
属本批任务中难度最高者。

## 7. 策略评估

> **⚠ 本节结论已被后续发现修正，见第 10 节。**
> 2026-08-20 定位到单臂本体在仿真执行环节的一处缺陷（左右两路夹爪指令写同一物理关节，
> 相互覆盖导致夹爪逐帧震荡），该缺陷影响本节所有成功率数据。
> 本节保留原始记录以说明排查过程，但其中的**成功率数字与"协变量偏移是唯一主因"
> 这一定性均需以第 10 节为准**。
> 不受影响的部分：模型在训练数据上的离线预测误差（0.044）、开环回放成功、观测比对结果。

本节记录评估过程中发现的问题、逐层排查方法与最终结论。
需要说明的是，**首轮评估得到的成功率数据不可用于评价混合训练的效果** ——
排查发现评估链路本身存在两处缺陷；而在修复缺陷后，性能不足的真实原因
被定位为模型泛化能力问题（第 7.5 节）。

### 7.1 评估设计

关键在于 `eval.sh` 的参数解耦：第二参数 `task_config` 决定**评估时所用的本体构型**，
第三参数 `ckpt_setting` 决定**加载哪个模型**。二者可以不同，
因而混合模型能够分别在两种构型上评估，直接检验其是否真正掌握了两种安装姿态。

| # | 模型 | 评估构型 | 检验目标 |
|---|---|---|---|
| 1 | place_object_stand 混合 | 桌面装 | 混合训练是否损害原构型性能 |
| 2 | place_object_stand 混合 | 侧装 | 混合训练是否掌握新构型 |
| 3 | turn_switch 混合 | 桌面装 | 同上 |
| 4 | turn_switch 混合 | 侧装 | 同上 |
| 5 | adjust_bottle 纯侧装 | 侧装 | 纯新构型数据的基线 |
| 6 | shake_bottle 纯侧装 | 侧装 | 纯新构型数据的基线 |

每组 100 个 episode（`test_num` 硬编码于 `script/eval_policy.py:162`），
指令类型为 `unseen`（使用训练中未出现的语言指令表述）。

### 7.2 判读标准

- 若第 1、2 组成功率相近且均不低，说明混合训练成功实现了跨构型泛化；
- 若第 2 组显著低于第 1 组，说明 50 条侧装数据不足以支撑新构型的学习，需增加数据量；
- 若第 1 组低于历史上纯桌面装模型的水平，说明混合训练对原构型造成了负迁移。

### 7.3 首轮结果与异常判断

| 模型 | 评估构型 | 成功率 |
|---|---|---|
| place_object_stand 混合 | 桌面装 | 4 % |
| place_object_stand 混合 | 侧装 | 3 % |
| turn_switch 混合 | 桌面装 | 0 % |

**这组数据未被采纳为结论。** 判断依据是：桌面装构型的数据与训练流程均未因本次工作
而改变，其成功率不应低至 4 %。四组结果全线异常（而非仅新构型偏低），
指向评估链路的系统性缺陷，而非策略本身的构型泛化能力。

由此转入逐层排查。

### 7.4 排查过程

采用"自外向内、逐层证伪"的方式，依次验证部署链路的各个环节。

**发现的缺陷一：加载了错误的权重文件。**
`policy/ACT/act_policy.py` 中硬编码加载 `policy_last.ckpt`，
而训练脚本同时保存 `policy_best.ckpt`（验证损失最优）与 `policy_last.ckpt`（末轮）。
本实验中最优 epoch 分别为 3446/6000 与 5581/6000，均远早于末轮；
结合 L1 曲线所示的过拟合，末轮权重的实际性能明显劣于最优权重。
数值比对确认二者权重不同（平均绝对差 4.6e-4 与 1.0e-4）。
已改为可通过配置或环境变量 `ACT_CKPT_NAME` 指定，默认行为保持不变。

**发现的缺陷二：左右腕相机在部署时互换。**
训练时的相机顺序取自 `SIM_TASK_CONFIGS`，为
`["cam_high", "cam_right_wrist", "cam_left_wrist"]`；
而部署代码中为 `["head_cam", "left_cam", "right_cam"]` —— 后两者顺序相反。
模型因此将左腕图像当作右腕输入。已修正为与训练一致。

**修复后成功率仍为 0**，说明尚有未查明的原因，排查继续。

**逐项证伪。** 下列环节经验证均无问题：

| 检查项 | 方法 | 结果 |
|---|---|---|
| 图像尺寸 | 读取训练 HDF5 的张量形状 | 均为 640×480，一致 |
| qpos 构造顺序 | 对比 `process_data.py` 与 `deploy_policy.py` | 均为 `left_arm + [left_gripper] + right_arm + [right_gripper]` |
| 色彩通道顺序 | 构造已知 RGB 数组，走一遍 `imencode`→`imdecode` | 数值不变，编解码对称，无通道颠倒 |
| 动作拆分逻辑 | 阅读 `_base_task.take_action` | 14 维按 6+1+6+1 正确拆分 |
| 归一化统计量 | 检查 `dataset_stats.pkl` 加载路径 | 正确加载 |
| 跨 episode 状态重置 | 检查 `reset_func` 调用位置 | 每 episode 前均调用 |

**关键的两项验证实验。**

*实验一：观测一致性比对*。用采集时的同一 seed 复现场景，
将仿真产生的观测与训练数据的第 0 帧逐项比对：

```
qpos 绝对差    : 0.0000（完全一致）
head 图像      : 视觉内容一致，逐像素平均差 17/255
                （差异来自背景纹理随机化，物体布局与机械臂位置完全对应）
```

*实验二：开环回放*。将训练数据中的真值动作序列直接送入仿真执行，
绕过模型推理：

```
执行 90 步后 check_success() = True  （第 89 步达成成功条件）
```

**开环回放成功，证明动作执行链路完全正常。** 结合观测比对结果，
问题被精确锁定于模型推理环节 —— 而模型在训练数据上的预测误差仅 0.044。

### 7.5 根因：协变量偏移

为解释上述矛盾，设计闭环诊断实验：从与训练数据相同的初始状态出发，
在仿真中运行模型，逐步记录模型预测与真值动作的偏差、以及仿真状态与真值状态的偏差。

| step | 预测误差 \|pred−gt_act\| | 状态偏差 \|sim_qpos−gt_qpos\| |
|---|---|---|
| 0 | 0.0423 | 0.0000 |
| 5 | 0.0638 | 0.0486 |
| 10 | 0.0413 | 0.0325 |
| 20 | 0.0696 | 0.0698 |
| 30 | 0.0691 | 0.0709 |
| 39 | 0.0667 | 0.0666 |

数据呈现出清晰的模式：

- **单步预测始终准确**。预测误差稳定在 0.04–0.08 区间，全程未发散，
  与模型在训练数据上的表现（0.044）处于同一量级。
- **但状态偏差持续累积**。从 0 单调增长至 0.07，与预测误差同步上升。

这是模仿学习中的经典**协变量偏移**（covariate shift / compounding error）：
策略在训练分布上表现良好，但执行中每步的微小误差使系统状态逐渐偏离训练分布，
而偏离后的状态又是策略未曾见过的，导致误差进一步累积，最终无法完成需要高精度的操作。

对照训练数据可知，相邻帧的动作变化平均仅 0.016 弧度，
而累积偏差已达 0.07 —— 约为单步动作幅度的 4 倍，足以使抓取类任务失败。

### 7.6 结论

**评估失败的根本原因是模型泛化能力不足，而非跨构型混合训练策略本身有问题。**

支撑该结论的完整证据链：

| 验证项 | 结果 | 排除的可能性 |
|---|---|---|
| 开环回放真值动作 | 成功（89 步） | 动作执行链路 |
| 仿真 qpos vs 训练数据 | 差异 0.0000 | 状态观测 |
| 仿真图像 vs 训练图像 | 视觉一致 | 视觉观测 |
| 模型在训练数据上预测 | 误差 0.044 | 模型权重与归一化 |
| 闭环 40 步预测误差 | 0.04→0.08，不发散 | 单步推理能力 |
| 闭环轨迹偏差 | 0→0.07 持续累积 | **← 真实瓶颈** |

需要强调的是，**本次评估未能回答"混合训练是否实现了跨构型泛化"这一原定问题**。
因为模型在其原本擅长的桌面装构型上同样失败，两种构型的对比失去意义。
该问题需在模型泛化能力改善后重新评估。

### 7.7 改进方向

按预期收益排序：

1. **增加数据量**。100 条轨迹训练 6000 epoch 导致明显过拟合
   （train L1 ≈ 0.03 / val L1 ≈ 0.30）。这是最直接有效的改进，
   建议每构型扩充至 150–200 条。
2. **调整训练轮数并引入早停**。当前最优 epoch 远早于末轮，
   后续训练不仅无益且加剧过拟合。
3. **启用 temporal aggregation**。ACT 原论文中该机制通过对多个时间步的动作块
   加权平均来平滑输出，可缓解误差累积。需注意其实现中
   `actions_populated = torch.all(actions != 0, axis=1)` 的判据
   会将任一维为 0 的合法动作误判为未填充，使用前需核实。
4. **增强域随机化**。使训练分布覆盖更宽的状态空间，提升对偏离状态的容忍度。

## 8. TinyVLA 混合数据重训

### 8.1 训练策略的选择

既有的 TinyVLA 模型（`place_object_stand`，checkpoint-2000）仅在桌面装数据上训练。
其 `trainer_state.json` 显示 `global_step == max_steps == 2000`，属正常训练完成
（epoch 6.35，loss 收敛于 0.073–0.088），而非中断。

**选择重新训练而非从该 checkpoint 续训**，理由如下：续训的本质是在原数据上继续优化，
无法引入侧装数据；而若更换数据集后仍沿用原有优化器状态
（momentum 与学习率调度均基于旧数据分布建立），面对新引入的构型反而构成负担。

### 8.2 数据组织

TinyVLA 的 `dataset_dir` 字段原生支持目录列表与 `sample_weights`，
因此混合数据集只需声明两个来源，无需像 ACT 那样复制并重新编号文件：

```python
"place_object_stand_mix": {
    'dataset_dir': [
        "data/sim-place_object_stand/demo_rm65b_single-50",
        "data/sim-place_object_stand/demo_rm65b_lateral_50-50",
    ],
    'episode_len': 200,
    'camera_names': ['cam_high', 'cam_left_wrist', 'cam_right_wrist'],
    "sample_weights": [1, 1]      # 两构型域随机化参数一致，故等权
}
```

### 8.3 训练配置与结果

模型 InternVL3-1B + UNet diffusion policy head，冻结视觉塔与骨干网络。

| 超参数 | 取值 |
|---|---|
| per_device_train_batch_size | 1 |
| gradient_accumulation_steps | 16（等效 batch 16） |
| learning_rate | 2e-5，cosine 调度 |
| noise_samples | 4 |
| chunk_size | 16 |
| max_steps | 4000 |
| 精度 | bf16 |

`max_steps` 取 4000 的依据：数据量由 50 条翻倍至 100 条后，
2000 步仅相当于 3.2 epoch；4000 步方与原模型的 6.35 epoch 相当，保证可比性。

训练于 2026-08-19 16:31 启动、21:34 结束，耗时 5 小时 03 分。

| 指标 | 纯桌面装基线 | 混合数据模型 |
|---|---|---|
| 训练步数 | 2000 | 4000 |
| epoch | 6.35 | 6.34 |
| 末段 loss | 0.073 – 0.088 | 0.043 – 0.095 |
| 平均 train loss | — | 0.1275 |

两者 epoch 数几乎相同，可比性成立。混合模型的末段 loss 范围略宽但整体相当，
表明**引入第二种安装构型并未增加训练难度** —— 这与第 6.4 节中 ACT 的观察一致。

产物：`checkpoint-{2000,2500,3000,3500,4000}`，各约 1.7 GB，
输出目录与原结果分离，原 checkpoint-2000 完整保留作为纯桌面装基线。

**注**：与第 7 节的结论相呼应，训练损失收敛不等同于任务成功率高，
该模型的实际性能仍需评估验证。

### 8.4 部署链路检查

鉴于第 7 节在 ACT 部署链路中发现了两处缺陷，评估 TinyVLA 前先对其部署代码
做了同类检查。结果表明该链路**此前从未被完整跑通过** ——
旧的纯桌面装模型同样受阻于下列问题。共发现并修复 5 处：

**缺陷一：图像被预先压成方图，视觉 token 数相差 12 倍（最严重）。**

`deploy_policy.py` 的 `encode_obs` 将三路相机图像 `cv2.resize` 至 448×448；
而训练侧（`data_utils/dataset.py`）直接使用 HDF5 中的 640×480 原图。
二者随后都进入 `InternVL3Process.load_image`，其内部的 `dynamic_preprocess`
会按宽高比动态切分图块：

```
训练 640×480 (4:3) → 12 个 448 图块
部署 448×448 (1:1) →  1 个图块
```

即模型在部署时接收到的视觉信息量仅为训练时的 1/12。
此问题与第 7.4 节 ACT 的相机顺序错误同属"训练—部署输入不一致"，
但影响更为严重。已修正为保持 640×480。

**缺陷二：加载出的是基座模型而非 TinyVLA。**

训练产出的 checkpoint 中，`config.json` 的 `architectures` 为 `"TinyVLA"`，
但 `auto_map` 仍沿用基座 InternVL3 的映射，指向 `InternVLChatModel`。
`load_model_for_eval` 经由 `AutoModelForCausalLM` 加载时会遵循 `auto_map`，
得到基座类实例，其上没有 `sample_action` 方法，推理时抛 `AttributeError`。

训练侧对此已有规避 —— `train_vla.py:110` 显式使用 `TinyVLAConfig`
而非 `AutoConfig`。评估侧改为同样显式指定 `TinyVLAConfig` 与 `TinyVLA` 类加载。

（排查中一度尝试将基座的 `modeling_internvl_chat.py` 等文件复制进 checkpoint 目录，
这反而坐实了错误的映射关系，属无效修复，已回退。）

**缺陷三：推理未禁用梯度。** `get_action` 缺少 `torch.no_grad()`，
前向过程保留全部激活值，36 个图块的推理直接耗尽 16 GB 显存。已添加装饰器。

**缺陷四：未安装 FlashAttention。** 三路相机各 12 图块共产生 9216 个视觉 token，
朴素注意力需实体化 9216×9216 的注意力矩阵，单次分配即达 4.48 GB。
安装 FlashAttention 2.6.3（预编译 wheel，匹配 torch 2.4.1+cu121 / cxx11abi=False）后
显存问题解决。

此处需注意训练与推理的显存需求并不对称：训练时冻结视觉塔、启用梯度检查点、
等效 batch 为 1，故 16 GB 可行；而推理无这些优化，反而更容易 OOM。

**缺陷五：指令类型不一致。**
`process_data.py` 为每条轨迹写入的 `language_raw` 是固定表述
（取自任务 JSON 的 `full_description`），即训练时模型只见过一种指令。
而评估默认 `instruction_type: unseen`，使用训练中未出现的指令模板，
会在动作策略之外额外叠加"指令泛化"这一变量。

运行时 `generate_episode_descriptions()` 只产出 `seen` / `unseen` 两类
（填写 `full_description` 会 `KeyError`），故取 `seen` —— 其模板出现于训练语料中，
语言分布更接近。**但即便如此，与训练时的单一固定表述仍存在差异，
这是本次评估无法完全消除的一项偏差。**

**对比小结**：ACT 的缺陷是"能运行但结果无效"（加载末轮权重、相机顺序颠倒），
TinyVLA 的缺陷是"根本无法运行"。前者更为危险 ——
它会产出看似合理、实则不可用的数字，若不加质疑便可能被当作结论。

### 8.5 评估结果

> **⚠ 本小节的成功率同样受第 10 节所述的夹爪缺陷影响，需重新评估。**
> 8.6 节的离线诊断（采样噪声、去噪步数扫描）不受影响，因其不经过仿真执行环节。

修复 8.4 节所述的 5 处缺陷后，评估链路可正常运行（推理速度约 2 分钟/episode，
显存占用稳定在 7.3 GB）。鉴于 VLA 推理开销远高于 ACT，先以 15 个 episode 做小规模验证。

**结果：0/15（桌面装构型）。**

与 ACT 的 4 % 同属接近零的水平。但进一步诊断表明，**两者的失败机理完全不同**。

### 8.6 失败机理诊断

沿用 7.4 节的方法，将训练数据直接送入模型，比较预测动作与真值：

| 采样方式 | frame 0 误差 | frame 10 误差 | 说明 |
|---|---|---|---|
| 单次采样 | 0.19 | 0.30 | 远大于 ACT 的 0.044 |
| 5 次采样取均值 | 0.17 | 0.11 | 明显改善 |

单次采样时，frame 0 的预测为 `[-0.802, 0.208, 0.002]`，而真值是 `[0, 0, 0]`
（初始静止姿态），首关节偏差达 0.8 弧度；但 5 次采样的均值为
`[-0.017, -0.031, 0.184]`，已接近真值。frame 10 同样如此
（均值 `[0.638, 1.014, 0.533]` vs 真值 `[0.617, 1.104, 0.441]`）。

**采样方差与误差同量级**（标准差 0.10–0.21，误差 0.11–0.17），
说明模型已学到大致正确的动作分布，问题出在单次采样的随机性过大：

```
训练数据相邻帧动作变化 : 0.016 弧度
单次采样标准差         : 0.10 – 0.21 弧度
=> 采样噪声约为有效动作幅度的 9 倍
```

**去噪步数不是原因。** UNet diffusion head 训练时加噪 100 步、推理默认只去噪 10 步，
一个自然的假设是步数不足。实测扫描该参数：

| 去噪步数 | 5 次采样均值误差 | 采样标准差 |
|---|---|---|
| 10（默认） | 0.200 | 0.207 |
| 30 | 0.196 | 0.140 |
| 50 | 0.296 | 0.109 |
| 100 | 0.403 | 0.100 |

增加步数确实使方差单调下降（0.207 → 0.100），但**均值误差反而上升**（0.200 → 0.403）。
这排除了"去噪不充分"的假设，表明模型学到的分布中心本身存在偏移，
增加采样精度只会更精确地收敛到偏移后的中心。

### 8.7 两套架构的失败机理对比

| | ACT | TinyVLA |
|---|---|---|
| 训练数据上的预测误差 | 0.044（准确） | 0.15–0.30（单次采样） |
| 闭环行为 | 单步准确，状态偏差累积 0 → 0.07 | 单步即有大幅波动 |
| 主导因素 | **协变量偏移** | **采样噪声 + 分布中心偏移** |
| 模型本身 | 无问题 | 未充分拟合 |

两者虽都表现为接近零的成功率，成因却截然不同。这一对比说明：
**仅凭成功率无法诊断问题，必须深入到单步预测层面才能区分"模型没学会"
与"模型学会了但闭环发散"。**

对 TinyVLA 而言，1B 参数量的模型在 100 条轨迹上训练 6.34 epoch，
数据量相对模型容量明显不足；其扩散头需要拟合的是动作分布而非单点，
对数据量的需求高于 ACT 的确定性回归。因此**扩充数据量对 TinyVLA 的意义更为关键**。

### 8.8 本节结论与限制

- TinyVLA 部署链路已修复至可用状态（此前从未跑通），修复内容具有复用价值；
- 混合数据训练本身收敛正常，未因引入第二种构型而增加难度；
- 但模型未充分拟合，**评估同样未能回答"混合训练是否实现跨构型泛化"的问题**；
- 仅完成桌面装构型 15 个 episode 的验证，侧装构型未评估 ——
  在模型本身尚未达到可用水平时，构型间对比无实际意义；
- `instruction_type` 取 `seen` 而训练用单一固定表述，此项偏差无法消除。

## 9. 单臂本体的夹爪指令冲突

本节记录一处平台级缺陷。它由一个朴素的疑问引出 ——
"用于验证的任务是否本身就不支持单臂？" —— 排查结论是任务支持单臂，
但**单臂本体在仿真执行环节存在夹爪指令相互覆盖的问题**。

### 9.1 任务侧的确认

`place_object_stand` 与 `turn_switch` 的 `play_once` 全程只使用一个 `arm_tag`
（依据物体位置选择左或右），不存在双臂协同动作。数据采集能够采满 150 条，
本身即是任务可由单臂完成的直接证据 —— 若需双臂，专家轨迹根本无法生成。

`place_object_stand` 的 `check_success` 要求 `is_left_gripper_open() and is_right_gripper_open()`，
初看似有双臂假设；但这两个值均由 `get_normal_real_gripper_val()` 从**实际关节驱动目标**读取，
单臂配置下二者指向同一物理关节，故必然相等，该条件自洽。

### 9.2 数据表示中的不对称

检查训练数据的 14 维动作后发现：

| 维度 | 被任务选中的一侧 | 未被选中的一侧 |
|---|---|---|
| 关节角 dim0–5 | 实际轨迹 | **完全相同**（同一实体） |
| 夹爪 dim6 | 随抓取变化（1.0 → 0.0） | **恒为 1.0**（张开） |

抽样 20 条 episode：13 条使用左臂、7 条使用右臂，无一条两侧夹爪同步变化。
即模型需要从视觉判断"本次用哪一侧"，进而只驱动对应侧的夹爪。

### 9.3 执行环节的缺陷

`envs/_base_task.py` 的控制循环对左右两侧**均**调用 `set_gripper`：

```python
self.robot.set_gripper(left_gripper[now_left_id], "left")
...
self.robot.set_gripper(right_gripper[now_right_id], "right")
```

单臂配置下两者写入同一物理关节，**后执行者覆盖前者**。
闭环诊断记录了模型预测与实际生效值（`real_L`/`real_R` 恒相等，因是同一关节）：

| step | gt_L | pred_L | pred_R | real（修复前） | real（修复后） |
|---|---|---|---|---|---|
| 38 | 0.020 | -0.027 | 0.981 | 0.000 | 0.000 |
| 39 | 0.000 | -0.034 | 0.979 | **0.300** | 0.000 |
| 40 | 0.000 | -0.036 | 0.978 | 0.000 | 0.000 |
| 41 | 0.000 | -0.039 | 0.979 | **0.200** | 0.000 |
| 43 | 0.000 | -0.038 | 0.978 | **0.200** | 0.000 |
| 45 | 0.000 | -0.044 | 0.976 | **0.100** | 0.000 |

**模型的预测是正确的**：`pred_L` 精确跟随真值从 0.908 降至 0（闭合抓取），
`pred_R` 稳定保持 0.98 左右（张开），说明它已学会"用左臂、右臂不动"。
但实际生效值在闭合与张开之间**逐帧震荡**，物体无法被夹住。

开环回放此前能够成功，是因为专家轨迹两侧的夹爪值在关键时刻恰好不冲突；
而模型输出的 `pred_R ≈ 0.98` 与 `pred_L → 0` 持续冲突。

### 9.4 修复

在控制循环前判断本体类型，单臂时只驱动实际在动作的一侧：

```python
single_arm_gripper_side = None
if self.is_single_arm_embodiment:
    left_dev  = max(abs(left_gripper  - 1.0))   # 偏离张开状态的程度
    right_dev = max(abs(right_gripper - 1.0))
    single_arm_gripper_side = "left" if left_dev >= right_dev else "right"
```

判断条件取自 `config.yml` 的 `dual_arm` 字段（描述本体物理形态），
**不可**使用 `Robot.is_dual_arm`（即 `dual_arm_embodied`，表示左右臂是否共用实体，
单臂本体亦为 True，误用会波及 aloha-agilex 等真双臂机器人）：

| 配置 | `config.dual_arm` | `dual_arm_embodied` | 新逻辑 |
|---|---|---|---|
| `[aloha-agilex]` | True | True | 不生效 |
| `[piper, piper, 0.6]` | False | False | 不生效 |
| `[rm65b]` / `[rm65b_lateral]` | False | True | **生效** |

改动为 22 行新增、2 行修改（原有两行 `set_gripper` 仅被条件包裹），
并保留 `envs/_base_task.py.bak-20260820` 备份。
回归测试：aloha-agilex 的 `beat_block_hammer` 采集正常。

### 9.5 修复效果与结论修正

修复后重新评估（15 episode，桌面装构型）：

| 模型 | 修复前 | 修复后 |
|---|---|---|
| ACT (mix-100) | 4 % (4/100) | 0/15 |
| TinyVLA (mix-100) | 0/15 | 0/15 |

**成功率未见改善。** 由此可得两条结论：

1. 夹爪震荡是真实缺陷（诊断数据明确），修复必要 ——
   它在物理上是错误的，任何单臂本体的抓取任务都会受影响；
2. 但它**不是**任务失败的唯一原因。第 7 节将失败归因于协变量偏移，
   该判断**方向正确但不完整** —— 当时的成功率数据中混入了夹爪缺陷的影响。
   修复后重测表明：即使排除夹爪问题，协变量偏移（关节角偏差累积至 0.07，
   为单步动作幅度 0.016 的 4 倍）依然足以致命。

需要说明的是，若不修复此缺陷，扩充数据后重训仍会撞上同一障碍，
且届时归因将更加困难 —— 两个独立成因叠加时，任何单一改动都看不出效果。

## 10. 评估基准的修正：成功率上限并非 100%

本节记录一处**贯穿全文的评价基准错误**。它使第 7、8、9 节中所有成功率数字的
解读都偏离了实际，也解释了为何连续三轮修复（夹爪覆盖、关节角覆盖、数据量增至 3 倍）
在成功率上均"毫无改善"。

### 10.1 问题的暴露

三轮修复后成功率始终为 0，且各轮的离线指标明明都在改善：

| 轮次 | 改动 | 离线指标 | 成功率 |
|---|---|---|---|
| 基线 | — | ACT 单步误差 0.044 | 4/100 |
| 第 9 节 | 修复夹爪指令覆盖 | 夹爪震荡消除 | 0/15 |
| 本节前 | 修复关节角指令覆盖 | 左右两路统一 | 0/15 |
| 第 8 节 | 数据量 100 → 300 | TinyVLA 采样误差 0.200 → 0.107（-47%） | 0/15 |

"离线全面改善、闭环纹丝不动"这一矛盾，最终指向评价基准本身。

### 10.2 评估场景的可行性

`script/eval_policy.py` 自 `st_seed = 100000 * (1 + seed)` 起**顺序**评估，
不对场景做任何可行性筛选。为确认这些场景的难度，让**专家策略**
（`play_once`，拥有完美的物体位姿信息与 curobo 运动规划器）在同一批 seed 上运行：

```
尝试 196 次，成功 30 次 —— 成功率 15.3%
```

失败原因包括物体不稳（域随机化的杂物挤倒目标）、运动规划失败
（`target_pose cannot be None`）、以及成功判据无法满足。

评估实际用到的前 15 个 seed（100000–100014）中，专家仅能完成 5 个。

### 10.3 结论：此前的成功率被系统性误读

**模型成功率的理论上限约为 33%（前 15 个 seed），而非 100%。**

此前将 "0/15" 解读为"完全失败"，据此推断模型存在严重缺陷，并展开了多轮修复。
但真实的对照是 **0/15 vs 专家的 5/15** —— 模型确有不足，
却远非此前判断的灾难性程度。

该基准错误同时使前三轮修复的评估结论不可靠：
样本量仅 15、其中可成功位仅 5 个，统计噪声极大，
修复前后同为 0 很可能只是**分辨率不足以体现改善**，而非改善不存在。

作为佐证，采集阶段 `place_object_stand` 采满 150 条用了 1091 次尝试
（成功率 13.7%），与评估场景的 15.3% 属同一量级 ——
两者场景分布一致，只是该任务本身难度就高。

### 10.4 修正后的评估方法

改为**仅在专家验证过可完成的场景上评估**，使成功率上限回到 100%，
从而将「任务难度」与「模型能力」解耦：

1. 用专家策略扫描 seed 空间，记录可完成的场景（本次得到 30 个，耗时约 196 次尝试）；
2. 策略模型只在这批 seed 上评估；
3. 所得成功率可直接解读为"模型达到专家水平的比例"。

该方法的代价是需要额外一轮专家扫描，但它消除了"任务难度"这一混杂变量，
使不同模型、不同修复之间的对比真正可比。

### 10.5 教训

本节的错误与第 7、8 节所记录的"训练—部署不一致"缺陷同属一类：
**程序照常运行、数字照常产出，但数字的含义与预期不符**。

区别在于，前者可通过检查代码路径发现，而本节的问题需要
**为评价指标本身建立参照系** —— 即先测量"完美策略能达到多少"，
再据此解读模型的得分。若缺少这一步，任何绝对数值都无法判断优劣。

推广而言：**在报告任何成功率之前，应当先确认该指标的可达上限。**

## 附录 A：一类隐蔽的环境故障

本实验期间，**所有**机械臂本体（包括原有的、与本次改动无关的构型）一度均无法运行，
报错为：

```
'Robot' object has no attribute 'left_planner'
```

由于故障恰好出现在新增侧装构型之后，最初误判为该构型引入的问题。实际根因有两层，
均与机器人配置无关：

**第一层：解释器环境错误。** 项目依赖安装于专用 conda 环境，而执行时使用了 base 环境，
导致报出一系列"缺少 open3d / sapien / mplib"的假象。依此假象所做的降级修复
进一步恶化了环境。

**第二层：NumPy 与 PyTorch 的 ABI 不匹配。** 环境曾经历 torch 2.4.1 → 2.5.1、
numpy 1.26 → 2.2.5 的升级，其后又将 numpy 降回 1.26.0，但 pip 未清理残留文件：
numpy 目录中同时存在 1.x 的 `core/` 与 2.x 的 `_core/`，
torch 亦有 2.4.1 与 2.5.1 两层叠加。

故障传播链如下：

```
numpy / torch ABI 不匹配
  → torch.from_numpy 报 "expected np.ndarray (got numpy.ndarray)"
  → curobo 构造 planner 时 torch.as_tensor(np.array(scalar))
     抛 TypeError: len() of unsized object
  → planner 构造失败，异常被上层捕获
  → 后续访问 self.left_planner 时报 AttributeError
```

最终暴露的异常与真实根因之间跨越三层调用，且异常信息中不含任何 numpy / torch 字样，
极易误判为业务逻辑缺陷。

**诊断要点**：`torch.from_numpy(np.array(1.0))` 报
`expected np.ndarray (got numpy.ndarray)` 是 ABI 不匹配的特征签名 ——
类型名称完全相同却判定为不同类型，说明 C 扩展所认知的内存布局与实际不符。

**修复**：连续多次执行 `pip uninstall`（直至提示 not installed）以清除全部叠加层，
再从本地 wheel 干净安装配套版本。最终环境为：

| 组件 | 版本 |
|---|---|
| Python | 3.10 |
| PyTorch | 2.4.1+cu121 |
| torchvision | 0.19.1+cu121 |
| NumPy | 1.26.4 |
| SAPIEN | 3.0.0b1 |
| mplib | 0.2.1 |
| curobo | 0.7.7 |

版本约束：`mplib` 要求 `numpy < 2.0`；PyTorch 与 NumPy 的大版本必须配套编译。

**经验**：诊断顺序应为「解释器路径 → 依赖版本配套性 → 业务配置」。
本次因跳过前两步，在错误方向上耗费了大量时间。
